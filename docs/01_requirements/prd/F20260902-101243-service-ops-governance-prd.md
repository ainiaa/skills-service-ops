# PRD：service-ops 运维能力治理文档

## 1. 背景与目标

### 1.1 背景

service-ops 已内置 SLS 日志检索、TraceId 排障、受控数据验证、Excel 导出与 PaaS 工单能力。此前能力、触发边界和证据完整性分散在脚本与 Skill 指令中，使用者难以快速确认何时自动触发、何时必须显式操作。

### 1.2 目标

建立与当前实现一致的运维治理文档：普通观测能力可自动发现，工单只能显式调用；排障结论必须说明证据失败或日志截断；健康检查按所选能力报告依赖。

## 2. 目标用户

| 用户角色 | 描述 | 核心需求 |
|---|---|---|
| 值班工程师 | 通过日志与 TraceId 定位故障 | 获得可确认、可追溯的排障结论 |
| 服务维护者 | 执行小范围数据验证或导出 | 在明确边界内安全使用生产数据 |
| 变更执行人 | 提交或操作 PaaS 工单 | 必须主动表达意图并经确认令牌保护 |

## 3. 功能需求

### 3.1 功能列表

| 编号 | 功能 | 优先级 | 描述 | 验收标准 |
|---|---|---:|---|---|
| FR-01 | 观测路由 | P0 | 自动发现 SLS、TraceId、只读验证和导出请求 | Skill 前置描述不含工单触发词 |
| FR-02 | 工单显式触发 | P0 | 工单仅在 `$skills-service-ops` 显式调用且意图明确时执行 | 隐含请求和排障上下文不得触发 `db_apply.py` |
| FR-03 | 证据完整性 | P0 | Trace 分析保留采集失败与截断服务 | `summary` 同时输出 `evidence_failed_services`、`truncated_services` |
| FR-04 | 就绪检查 | P1 | 根据 `all`、`paas` 或 `sls` 检查必要依赖与凭据 | `paas` 不要求 SLS SDK；`sls` 不要求 MySQL/Excel 依赖 |

### 3.2 用户故事

1. 作为值班工程师，我希望看到日志是否被截断，以便不把不完整证据当成根因结论。
2. 作为服务维护者，我希望只检查当前所需能力的依赖，以便首次配置不会被无关模块阻塞。
3. 作为变更执行人，我希望工单不会因普通排障对话而触发，以便避免误操作。

### 3.3 用例分析

#### UC-001：TraceId 排障

- **参与者：** 值班工程师。
- **前置条件：** 指定 TraceId、服务和环境，SLS 凭据已配置。
- **主要流程：** 收集日志，分析错误、告警和上下文；若截断或失败，在报告中标记证据状态。
- **后置条件：** 输出已确认、待验证、证据不完整或证据采集失败的结论。

#### UC-002：显式工单

- **参与者：** 变更执行人。
- **前置条件：** 用户显式调用 `$skills-service-ops` 并说明具体操作。
- **主要流程：** 预检 SQL，展示 confirmation token，取得一致确认后才提交。
- **后置条件：** 仅报告平台返回的工单状态。

## 4. 非功能需求

- **安全：** 凭据不写入配置、命令参数或输出；变更不自动触发。
- **可靠性：** 失败与截断均不可被解释为空日志或成功。
- **可维护性：** 文档和脚本输出字段名称保持一致。
- **可用性：** 健康检查显示当前能力真正缺少的依赖。

## 5. UI/UX 需求

无图形界面；通过 Skill 路由、命令帮助和结构化 JSON 输出提供操作反馈。
